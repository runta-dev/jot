# R3.1 — localize before enumerating edits

Preregistered before execution. Pure Jev, no generative model or reference-derived proposals.

Hypothesis: a small set of parallel, speculative questions can identify the edit type and likely location, retaining the correct edit while reducing R3's exhaustive-neighborhood cost.

Stage 1: Choice over no-op, character insertion/replacement/deletion/transposition, word insertion/replacement/deletion, or whitespace normalization. Independent location Choices describe every eligible position in context, under explicit hypothetical edit-type premises. These questions cannot see each other's answers. Code consumes only the selected action's location distribution, keeping its top two locations.

Stage 2: enumerate all allowed characters or the fixed function-word list at those two locations, always including original. Compare complete candidate texts with Choice. No iterative retries after an incorrect answer. At most two API calls per draft (unless transport retry).

Cases: R3's eight development drafts plus eight new frozen probes, with five corruptions and three correct controls. Gold strings remain local. New probes are untouched by method tuning during this run. Fixed function words include by/from and common auxiliaries; character alphabet is fixed. Location/character choices remain <=255.

Report exact match, preservation controls, proposal recall, no-op failures, actual tokens and end-to-end latency. Advancement gate: >=9/10 corruptions repaired across both sets, all 6 correct controls unchanged, plus lower mean reported input tokens than R3. This is a development gate, not evidence for generation from empty or arbitrary conversation quality.
